Summary

We will build fused CUDA INT8 and INT4 linear-layer kernels for small-batch LLM decoding on the NVIDIA RTX 2080 GPU. We will compare the three compute paths the GPU supports (FP16 fused multiply-adds, dp4a INT8 dot products, and tensor cores) across weight formats, scale granularities and batch sizes, and use the measurements to build a cost model that selects the best kernel for each layer shape and batch size. We will integrate the kernels into vLLM through its quantization plug-in interface and measure the effect of quantized linear layers on request throughput, KV-cache capacity and output tokens per second at fixed VRAM with Llama 3.2 1B and 3B.

Background

Decode linear layers

LLM inference has a prefill phase, which processes the prompt as one large matrix multiply, and a decode phase, which generates one token per step. In decode, each transformer layer runs the current token's hidden vector through seven linear layers, including the Q, K, V and output projections in attention and the up, gate, and down projections in the MLP, each of which is a multiply by a weight matrix. For Llama 3.2 1B these are matrices of size 2048×2048, 2048×512 and 8192×2048. With one request, each is a matrix-vector product, while with a small batch of concurrent requests, it is a matrix multiply with a very narrow right hand side. Per step, every weight in the model is read once and used for only B multiply-adds, so decode is bound by memory bandwidth rather than compute in the roofline model, and thus its latency is roughly the size of the weights divided by bandwidth.

Quantization

Quantization stores each weight as a small integer plus a shared scale, so an INT8 weight is half the bytes of FP16 and an INT4 weight is a quarter. Since a decode step is bounded by the bytes of weights it reads, fewer bytes per weight translates directly into lower latency, provided the kernel can stream the compressed weights at the same bandwidth and the unpacking does not become the new bottleneck. With a per-row scale, every weight in an output row shares one scale. With group-wise scales, every 32 to 128 consecutive weights along K share one, which results in less quantization error but more scale loads. It is possible to quantize only the weights (W8A16, W4A16), keeping the activations in FP16 and converting each weight back to FP16 just before the multiply. The computation is then unchanged and only memory traffic is saved. This conversion can happen in one of two places. In the two-step approach, a separate kernel first dequantizes the entire weight matrix into an FP16 copy in GPU memory, and an ordinary FP16 matrix multiply then runs on that copy. In the fused approach, the matrix kernel reads the packed integers directly and converts each weight in registers before using it, so no FP16 copy is ever written, which saves bandwidth. Quantizing the activations (W8A8, W4A8) rounds the activations to INT8 per token at runtime, which allows the multiply to run on integer units, with the scales applied once to the final sum to produce an FP16 output. Smaller weights also free GPU memory, which a serving engine can spend on KV cache and therefore on more concurrent requests.

What benefits from parallelism

Output rows are independent, so they spread across SMs and warps. Within a row, the dot product over K splits across threads with a reduction. Across a batch, the same weight tile serves every request, which allows for reuse and is what a tiled GEMM exploits. Turing offers three units for the multiply, FP16 fused multiply-add on CUDA cores, dp4a integer dot products on CUDA cores, and tensor cores in FP16 and INT8 modes, and each has a different balance of instruction cost, data staging, and wasted work at small batch.

State of the art on Turing

Marlin is the tensor core 4-bit kernel that many serving engines default to. It was ported to Turing in late 2025 [Lin, 2025], replacing its cp.async pipeline with synchronous loads. Its own 2080 Ti benchmark shows a speedup of only 1.7x to 3x over FP16 at batch sizes 1 to 8 despite reading 4x fewer bytes, and the gap is largest on the smaller layer shapes of 1B to 3B models. That benchmark compares only Marlin and Exllama, which differ in layout, pipelining, accumulation, and compute path, so it cannot say which design choice accounts for the difference between the kernels or whether a CUDA-core kernel built with the same techniques as Marlin would close it. Production engines also dispatch inconsistently at small batch, with TensorRT-LLM and llama.cpp using CUDA-core kernels below a batch threshold, while vLLM uses Marlin throughout. Our goal is to investigate the design space and determine which kernel is best for each layer shape and batch size.

The Challenge

The challenge is to turn the smaller weight matrices that quantization produces into lower decode latency. The kernel must stream packed weights at close to peak bandwidth while overlapping unpacking, scaling, and reduction with the memory movement, and the best way to do that may change with layer shape and batch size. More specifically, we identify the following challenges:

  • Work decomposition and reductions. In Y = WX each row of W is an output feature and the dot product runs over the hidden dimension K (2048 for Llama 3.2 1B and 3072 for 3B). Requests are columns of the activation matrix X. At small batch sizes, the work can be split over the output rows and the K dimension. Splitting over rows alone cannot fill 46 SMs on small-N layers such as the K and V projections, while splitting over K adds a reduction over blocks. Since group scales occur every 32 to 128 elements, partial sums need to be rescaled at every group boundary.
  • Memory locality and packed layout. Weights must be streamed once with coalesced loads, so the packed layout must place values that a thread needs together in each 32-bit word (four INT8 or eight INT4 values), and unpacking them costs instructions in the inner loop.
  • Three compute paths. FP16 FMA and dp4a run on CUDA cores, whose instruction issue rate becomes the limit as the batch size grows. Tensor cores make the multiply nearly free but require weights staged into fragments and block-level synchronization. At batch size 1, using tensor cores also results in redundantly computing 16 columns when only 1 is needed. Production systems disagree on which path is fastest on small batches. TensorRT-LLM and llama.cpp dispatch to CUDA-core kernels below a batch threshold, while the Turing port of Marlin beats Exllama's FMA kernel at a batch size of 1.
  • No asynchronous copies. Turing lacks the cp.async instruction, so overlap of the next tile's loads with the current tile's math must come from register double-buffering, which costs occupancy.
  • Batching. Running B requests as B GEMVs streams and unpacks the weights B times. A tiled GEMM reads the weights once, but since tensor core tiles are at least 16 wide in the batch dimension, they waste work below batch size 16. A tiled GEMM also needs shared memory for activations and leaves SMs idle on small N. As a result of these tradeoffs, whether to use a tiled GEMM or independent GEMVs is shape-dependent.
  • Two sources of error. Quantization introduces rounding error that is larger for INT8 activations than for weights, and because FP32 accumulation runs at half rate on Turing's tensor cores, kernels are pushed toward FP16 accumulation, which adds error over long dot products. Kernel bugs are the other source. Results must match a quantized PyTorch reference exactly and the FP16 model closely.
  • Kernel selection. Because the winning kernel changes with shape, batch and format, a cost model encompassing bandwidth, fixed-cost, and occupancy terms must correctly predict the winner from a small set of benchmarks and be validated against a full sweep.
  • Serving integration. On top of replacing the linear layer in the serving engine, we will need to demonstrate that freed weight memory becomes KV cache and enables more admitted requests and more output tokens per second, which involves the scheduler, memory manager and CUDA-graph capture.
